# JHONNY AI — Phase 6 integration and release readiness

This continues the Phase 2 React/Vite application and Phase 3 FastAPI backend. Existing UI routes and features remain. Phase 4 adds server-backed Library, Studio project, and Admin moderation panels, public-library visibility rules, project duplication/deletion, and session revalidation on refresh/expiry.

## Architecture

- **Frontend:** React 19, TypeScript and Vite (existing application). `src/lib/api.ts` is the shared HTTP client; the login and registration screens call the API, and the creator upload flow sends the actual file with progress reporting.
- **Backend:** FastAPI + Pydantic validation; SQLite with foreign keys and indexes. Schema creation is idempotent at startup (`backend/app/main.py`); SQLite schema changes should be introduced as numbered SQL migrations before production deployments.
- **Auth:** PBKDF2-HMAC-SHA256 password hashes; opaque random bearer tokens, with only SHA-256 token hashes stored server-side; expiry and logout are enforced on every authenticated route. New registrations can only receive `user`; creator/admin roles must be assigned by a trusted operator. Frontend role state is for display only and is not backend authorization.
- **Media:** uploads are stored under `backend/data/media`, outside the frontend's public root. Names are generated by the server. FFprobe must be installed and on `PATH`; uploads fail closed if metadata cannot be verified. Default maximum upload is 500 MiB.
- **Rendering:** a FastAPI background task starts FFmpeg without blocking the request handler and exposes job status. This is a single-process development job runner, not a durable distributed queue; jobs are not automatically recovered after a server crash. Phase 4 Studio panel submits jobs only for saved projects with an owned source clip and valid trim settings.

## Windows setup

Install Python 3.11+ and Node.js 20.19+ (or a version compatible with the Vite version in `package.json`). Install FFmpeg/FFprobe and add their `bin` directory to `PATH` for upload validation and rendering.

Open PowerShell in the project root:

```powershell
Copy-Item .env.example .env
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r backend\requirements.txt
npm install
$env:JHONNY_DATA_DIR = (Join-Path (Get-Location) 'backend\data')
$env:JHONNY_DB_PATH = (Join-Path (Get-Location) 'backend\data\jhonny.sqlite3')
$env:JHONNY_CORS_ORIGINS = 'http://localhost:3000,http://127.0.0.1:3000'
uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

Keep the backend terminal open. In a second PowerShell terminal, from the project root:

```powershell
.\.venv\Scripts\Activate.ps1
npm run dev
```

Open `http://localhost:3000`. Set `VITE_API_BASE_URL` in a `.env.local` file before starting Vite if the API is not at `http://127.0.0.1:8000`.

## API endpoints

All authenticated endpoints require `Authorization: Bearer <access_token>`.

| Method | Endpoint | Purpose / authorization |
|---|---|---|
| GET | `/api/health` | Health check |
| POST | `/api/auth/register` | Register user account (creator/admin role assignment rejected) |
| POST | `/api/auth/login` | Verify password and create expiring session |
| GET | `/api/auth/me` | Current authenticated user |
| POST | `/api/auth/logout` | Revoke current session |
| POST | `/api/clips/upload` | Creator/admin; validated multipart video upload; creates Pending clip and Pending Review license |
| GET | `/api/clips?q=&status=&sort=&page=&page_size=` | Paginated clip records; anonymous visitors receive only published clips with active, unexpired licenses; authenticated owners see their own records and admins can filter statuses |
| GET | `/api/clips/{id}` | Public published/licensed clip, or owner/admin record |
| GET | `/api/clips/{id}/download?requested_use=personal` | Published clip + active unexpired license + allowed use; records request then streams file |
| POST | `/api/projects` | Create owner-scoped Studio project |
| GET | `/api/projects` | List own projects |
| PUT | `/api/projects/{id}` | Update own project (admin override) |
| POST | `/api/projects/{id}/duplicate` | Duplicate own project |
| DELETE | `/api/projects/{id}` | Delete own project (admin override) |
| POST | `/api/projects/{id}/renders` | Validate source and render options; enqueue background render job |
| GET | `/api/renders/{id}` | Owner/admin render status and download URL when complete |
| GET | `/api/renders/{id}/download` | Download completed render as owner/admin |
| PUT | `/api/admin/users/{id}/role` | Admin-only promotion/demotion between user and creator; admin role is operator-provisioned |
| GET | `/api/admin/submissions` | Admin-only pending submissions |
| POST | `/api/admin/clips/{id}/moderate` | Admin-only approve/reject/suspend/remove; approval requires active unexpired license |
| PUT | `/api/admin/clips/{id}/license` | Admin-only license status and permitted-use update; activation requires a documented rights-verification note |

## Tests and limitations

Backend tests: from project root, activate `.venv`, install `backend/requirements.txt`, then run `python -m pytest backend/tests -q`. Frontend checks: `npm test`, `npm run lint`, and `npm run build`.

This is a local-development Phase 3 foundation, not a production security certification. Before public deployment: use HTTPS; move tokens to secure HttpOnly cookies or a hardened identity provider; add rate limiting, CSRF protections if cookie auth is used, email verification/password reset, audit-log retention, malware scanning, storage quotas, resumable/chunked uploads, a durable job queue, worker isolation, database migrations and backups, license-policy review, and production object storage. Render progress is coarse-grained (queued/running/completed/failed), not FFmpeg frame-level progress. The Phase 2 local/demo clip catalog and its original Admin table are retained for compatibility and are clearly separate from the new live backend panels. Some legacy analytics, rights registry, clip-detail interactions, and the original Studio editor still use local/demo data; use the explicitly labeled backend panels for server records and do not treat demo content as real licensed media.


## Phase 4 integration notes

- The Library page includes a **Live Library · Backend** panel. It requests paginated API data, server-side search/sort, and never substitutes mock content if the request fails. Anonymous responses are filtered on the server to Published + Active license + unexpired records. The pre-existing local demo catalog remains below it to avoid deleting Phase 2 demo workflows.
- Studio includes **Saved Studio Projects · Backend** for server CRUD, duplication/deletion, and render-job submission/status/download. It is separate from the legacy local project editor. Rendering requires a source clip owned by the signed-in account and valid `trim_start`/`trim_end` settings saved on the project. The panel currently exposes job refresh manually rather than a continuous progress poll.
- Admin Clip Moderation includes **Real Moderation Queue · Backend**, with server-side protected moderation actions and license verification note. The legacy demo moderation table remains below. Other Admin analytics, creator, report, and rights-registry pages have not all been migrated to server-backed data.
- A stored browser session token is revalidated against `/api/auth/me` on application startup. An API 401 clears the token and current client session. Backend authorization remains authoritative.
- Backend test command: `python -m pytest backend/tests -q`. Frontend commands: `npm test`, `npm run lint`, and `npm run build` after dependencies have been installed in a permitted environment.


## Phase 5 additions and current limits

- Clip detail routes now load by backend clip ID or a normalized title slug. The page fails closed with explicit loading/error/not-found states rather than silently using the local demo clip when the backend fails. It shows server publication/license status and only offers download when the current server-reported policy allows personal use. The backend intentionally does not expose private media paths, original storage filenames, owner IDs, or moderation notes. A thumbnail is not currently stored by the backend; the detail page displays a neutral placeholder rather than inventing one.
- Download records are written after Starlette completes sending the media response; denied requests are not counted as successful downloads. The client uses the response's server-provided filename when available and rejects empty response bodies. Every request still re-checks publication and license status.
- Added admin-protected analytics, user listing, creator listing, license registry, moderation history, and report listing/status endpoints. Public report submission validates fields and persists records. Analytics count only data this backend actually tracks; it does not claim views, category performance, or conversion metrics.
- Render job polling refreshes automatically every 2.5 seconds and clears its interval on unmount/job change. A global cap limits queued/running jobs; this remains an in-process FastAPI background task runner and is not durable across restarts.
- AI suggestion template duration is now deterministic rather than randomized.

## Phase 8 security hardening

Phase 8 adds SQLite-backed request limits for public registration, login attempts, public copyright/report submissions, creator uploads, and render-job creation. A rejected request receives HTTP `429 Too Many Requests` with a `Retry-After` header. Rate-limit events are stored in the configured application database and records older than 24 hours are pruned during requests.

Default limits:
- Registration: 8 attempts per email/IP pair per hour.
- Login: 10 attempts per email/IP pair per 5 minutes.
- Public reports: 5 submissions per reporter-email/IP pair per hour.
- Uploads: 12 attempts per creator/IP pair per hour.
- Render creation: 10 requests per user/IP pair per hour.

These controls are an initial mitigation, not a complete production anti-abuse system. Deployments behind a reverse proxy must configure trusted client-IP handling at the proxy/application boundary; do not blindly trust arbitrary `X-Forwarded-For` headers. Multi-instance deployments should use a deliberately shared rate-limit store and operational monitoring. Rate limiting does not replace CAPTCHA/abuse review, upload scanning, quotas, or infrastructure-level denial-of-service protection.
